## 3. 구현하면서 정해진 것 (문서에 반영 완료)

### ① 발송은 LEFO — 출고와 반대 방향
풀필먼트는 도착까지 3~5일, 판매까지 더 걸린다. 임박분을 보내면 팔리기 전에 만료된다.
그래서 **발송만 유통기한이 넉넉한 로트부터** 고른다. 나머지(출고·일일 반영·팝업 반출)는 FEFO.
→ `src/lib/fefo.ts`의 `planAllocation(lots, qty, strategy)` 하나로 처리.
→ 팝업 반출이 FEFO인 것은 실무 확인 완료.

### ② 재고를 바꾸는 통로는 하나뿐
`src/lib/stock.ts`의 `applyMovement()` 외에는 `lot.update()`를 직접 호출하지 않는다.
재고 변경과 이력 기록이 항상 같은 트랜잭션에서 함께 성공하거나 함께 롤백된다.
**새 기능을 만들 때도 이 함수를 통해야 한다.**

### ③ 시드는 앱과 같은 함수를 쓴다
`prisma/seed.ts`는 로트를 손으로 지정하지 않고 `applyMovement` + `allocateLots`를 통과시킨다.
사건은 **시간 순서대로**(95일 전 입고 → 85일 전 발송 → … → 어제 반영) 실행한다.
덕분에 발송 규칙을 LEFO로 바꿨을 때 시드는 코드 한 줄 안 고치고 따라왔다.
풀필먼트의 임박 재고도 "임박한 걸 보냈다"가 아니라 **86일 전 보낼 땐 108일 남았는데 시간이 지난 것**으로 만들어진다.

### ④ 시드는 자동 증가 번호까지 초기화한다
안 하면 `seed:reset` 때마다 ID가 밀려서 로그인 쿠키가 없는 사용자를 가리키고(외래키 오류),
`/products/1`이 404가 된다. 실제로 이 버그가 났고 고쳤다.

### ⑤ 세션은 DB까지 검증한다
`src/lib/auth.ts`의 `requireUser()`가 사용자 존재를 확인하고, 없으면 쿠키를 지운다.
**주의**: 이 파일은 Prisma를 쓰므로 `src/proxy.ts`(미들웨어)에서 import 하면 안 된다.
미들웨어는 JWT 검증만 하는 `src/lib/session.ts`를 쓴다.

### ⑥ 일일 반영은 '출고 0건'도 저장할 수 있다
어제 출고가 없었던 날에도 저장이 돼야 `lastReflectedAt`이 갱신되어 홈 할 일에서 사라진다.
막아 두면 그 거점이 영원히 미반영으로 남는다. 버튼 문구가 `어제 출고 없음으로 반영`으로 바뀐다.
반영 저장은 **입력 → 저장 → 목록 복귀** 한 번에 끝난다 (3사를 이어서 처리하기 위해서다).

### ⑦ 팝업 정산은 로트별 잔여 · 시식은 상품별
어느 유통기한이 시식으로 나갔는지는 아무도 모른다. 그래서 시식은 상품 단위로 받고
**임박한 로트부터** 시식으로 처리한다(FEFO). 잔여 복귀는 반품이 아니라 위치 이동이므로 사유가 없다.
정산 계산은 `src/lib/popup.ts`의 `settlePopupTx()`에 있다 — 액션과 테스트가 같은 함수를 쓴다.

### ⑧ 수량은 숫자로 저장하고 화면에서만 단위를 붙인다
DB `quantity`는 정수. 단위는 `Product.unit`(기본 `개`)에 한 번만 둔다.
표시는 `<Qty>`, 입력은 `<QtyInput>` 컴포넌트를 쓴다.

## 3-2. 하네스에서 정해진 것 (2026-09-16)

앱이 아니라 **작업 방식**을 정한 세션이다. 상세는 [loop.md](harness/loop.md) · [ssot.md](harness/ssot.md).

| # | 정한 것 | 왜 |
|---|---|---|
| ① | 이슈 템플릿은 **yml 폼 → md 한 칸** | 밖에서 쓴 계약서를 통째로 붙여넣게. 요청 비용이 폼 검증보다 중요하다 |
| ② | 폼이 받는 것은 **계약 6개 항목** | 4번은 "테스트 코드 기능명" — 기계 검증은 `npm run verify` 고정이라 요청자가 답할 것은 "어느 테스트가 판정하나" 하나뿐 |
| ③ | **검증과 루프의 책임 분리** | 검증은 판정만 한다(회차를 모른다), 루프는 반응만 한다(판정을 못 바꾼다) |
| ④ | 루프 정책을 **`harness/loop.md` 로 분리** | SSOT 는 경계 선언, 운영 절차는 `verification.md` 와 같은 층위에 둔다 |
| ⑤ | **1회 = 고치고 `npm run verify` 를 돌리기까지** | 실패 종류로 나누면 판단이 끼어들어 다음 세션이 회차를 다시 셀 수 없다 |
| ⑥ | 루프는 **상한 N 을 받고 열린다.** n 이 N 에 닿으면 중단 | 셀 수 없는 루프는 멈출 줄도 모른다. "한 번만 더" 는 한도를 없애는 것과 같다 |
| ⑦ | 멈추는 모든 경우를 **`NEED_HUMAN · 이유 · n/N`** | 산문으로 적으면 나중에 찾지 못한다. `need-human` 라벨은 색인일 뿐 — **원본은 이슈 댓글** |
| ⑧ | 루프 상태는 **이슈 댓글**에 쓴다 | 세션이 끊기면 남는 것은 Issue 와 git 뿐이다 |
| ⑨ | **계약이 그대로면 차감, 사람이 바꾸면 루프 종료** | 요구사항이 흔들릴 때마다 AI 예산이 깎이면, AI 는 요구사항 변경을 말리고 코드를 더 미는 쪽을 고르게 된다 |
| ⑩ | **머지가 루프를 닫는다** — 로컬 통과는 제출 자격 | 판정자는 둘(내 기계 · CI), 승인자는 하나(사람) |
| ⑪ | CI 다음은 **세 갈래** (머지 · 다시 구현 · 사람 판단) | ②와 ③을 가르는 것은 "계약이 그대로인가"와 "로컬에서 재현되는가" 둘뿐 |
| ⑫ | PR 경계는 **"회차를 쓰는가"** 하나 | 닫을 루프가 없는 변경에 PR 을 씌우면 승인자와 작성자가 같아진다 |
| ⑬ | CI **통과 뒤**에 **LLM review 를 자문**으로 (⑥-b) | 종료 조건을 오독하면 그 해석대로 테스트를 써서 실패 없이 통과한다 — 회차로도 CI 로도 못 잡는다. 앞(PR 전)에 두면 AI 가 사실을 정하게 되고 리뷰 왕복이 무한해지므로, **사실이 난 뒤 · 사람이 고르기 전**에 세운다. 회차를 쓰지 않고, 권고는 기존 세 갈래를 가리킬 뿐이다. 세션이 CI 를 추적하므로(`gh run watch`) **잡 등록 없이** 같은 흐름 안에서 별도 컨텍스트로 돈다 |

**역할 3분할** — 사람은 **기준**(종료 조건 · 상한 · 승인), 기계는 **사실**(통과인가 아닌가),
AI 는 **행동**(무엇을 고치고 언제 넘길까)을 정한다. AI 가 기준을 건드리면 완료를 자기가 정의하는 것이고,
사실을 건드리면(`--no-verify` · CI 재실행) 판정을 자기가 하는 것이다.

**이번 세션에 실제로 돈 작업:** 이슈 #4 (반출서 가용 재고 안내) — 계약 6개 항목으로 열고
구현 · 검증 · 종료까지. **루프 2/3 사용** (`7b56967`). 테스트 19 → 22건.

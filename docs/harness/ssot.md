## 4. Issue — 개별 작업의 SSOT

이 문서는 **제품**의 SSOT, Issue 는 **한 작업**의 SSOT.
작업 중 판단이 갈리면 Issue 를 먼저 본다. 여기 없는 것은 작업 범위가 아니다.

**흐름:** 요청자가 [요청 템플릿](../../.github/ISSUE_TEMPLATE/maintenance.md)에 **6개 항목**을 적어 Issue 를 연다 → 비거나 모호한 항목은 에이전트가 댓글로 정리한다 → 사람이 확정하면 시작한다.
템플릿은 마크다운 한 칸이다 — 밖에서 써 온 계약서를 통째로 붙여넣어도 된다. 5·6 은 기본값이 채워져 있고, 기계 검증은 `npm run verify` 고정이므로 4번에는 **그 안의 어느 테스트가 판정하는지**를 적는다.

### 작업 계약 6개 항목

| # | 항목 | 답하는 물음 |
|---|------|-----------|
| 1 | 배경 | 왜 필요한가 |
| 2 | 변경할 내용 | 어디를 고치나 |
| 3 | **종료 조건** | 무엇이 참이면 완료인가 |
| 4 | **기계 검증** (테스트 코드 기능명) | 어느 테스트가 완료를 판정하나 |
| 5 | 건드리면 안 되는 것 | 경계는 어디인가 |
| 6 | 구현 루프 최대 횟수 | 몇 번까지 재시도하나 |

### 규칙

- **6개 항목이 비면 시작하지 않는다** — 계약이 없으면 완료를 판정할 수 없다
- **Issue 와 이 문서가 충돌하면 이 문서가 이긴다** — 고칠 것은 Issue 다. 작업이 스펙을 바꾸지 못한다 (§3)
- **Issue 범위 밖을 고쳐야 하면 새 Issue** — 조용히 넓히지 않는다
- **종료 조건 한 줄에 §6 검증 명령 하나를 붙인다** — 붙일 명령이 없는 줄은 종료 조건이 아니다
- **종료 조건은 정상 · 경계 · 거부 · 불변 4줄로 쓴다** — 거부는 "지정 에러를 던진다"로 판정한다

### 종료 조건 쓰는 법

참/거짓이 기계적으로 갈려야 한다.

| 축 | 되는 예 | 안 되는 예 |
|----|--------|-----------|
| 형태 | 관계식 · 불변식 | 그 순간의 관찰값 |
| 수량 | `파손 = 반출 − 판매 − 시식 − 반품` | `파손이 12 로 나온다` |
| 날짜 | `today() + 7` 이내면 임박 | `2026-09-22 이전이면 임박` |
| 판정 | 명령어가 판정 | 화면에서 확인 |

구체적 숫자는 **재현 입력(1. 배경)에만** 쓴다 — 종료 조건에 박으면 그 한 케이스만 맞아도 통과해 버리고, 시드가 바뀌거나 다음 날 돌리면 깨진다.
날짜는 `src/lib/date.ts` 의 `today()` · `addDays()` 로 만든다 (`tests/stock-invariant.test.ts` 가 쓰는 방식).

## 6. 검증

**책임: 판정한다.** 지금 통과인가 아닌가만 말한다. 몇 회차인지는 모른다 (§7).

`npm run verify` — prepare → types → lint → test → build. 실패하면 멈춘다.
검증 전용 `verify.db` 를 쓴다. `dev.db` 는 건드리지 않는다.
보호 영역이 바뀌면 CI 가 경고를 남긴다. 막지는 않는다 — 승인은 PR 리뷰에서 한다 (§3).

[자세히](verification.md)

## 7. 구현 루프

**책임: 반응한다.** 판정에 대고 다시 할지 사람에게 넘길지 정한다. 판정 자체는 바꾸지 못한다.

**전역 기본값: 3회.** 작업별 한도는 각 Issue 6번이 덮어쓴다 (§4).

|  | 검증 (§6) | 루프 (§7) |
|---|---|---|
| 하는 일 | 통과인가 아닌가 | 재시도인가 넘김인가 |
| 아는 것 | 코드와 종료 조건 | 회차와 실패 이력 |
| 모르는 것 | **회차** | — |
| 못 하는 것 | — | **판정을 바꾸는 것** |

회차에 따라 기준이 달라지면 그것은 판정이 아니다. 루프가 고칠 수 있는 것은 **코드뿐**이다 —
종료 조건·테스트 기대값·보호 영역을 고치고 싶어지는 순간이 곧 멈춤 신호다.

### 세는 규칙

**1회 = 코드를 고치고 `npm run verify` 를 돌리기까지.** 실행이 회차의 경계다.

| 상황 | 셈 |
|---|---|
| 고치고 `npm run verify` 실행 | **1회** — 어느 단계에서 깨졌든 똑같이 1회 |
| 부분 실행 (`tsc` · `lint` · 단일 테스트) | 0회 — 같은 회차 안의 작업 |
| 통과한 뒤의 재실행 | 0회 — 통과로 루프는 이미 끝났다 |
| 코드를 안 고치고 재실행 | **즉시 멈춤** — 재현 안 되는 실패를 눈감는 것 |
| 요청이 바뀜 | 루프 아님. **새 계약** |

실패 종류로 나누지 않는 이유는 **회차가 관찰 가능해야** 하기 때문이다.
"이건 사소하니 안 센다"가 들어가면 판단이 끼어들고, 이어받는 세션이 회차를 다시 셀 수 없다.
verify 실행은 로그에 남는다 — 남는 것만 센다.

### 멈춤선 (하나라도 걸리면 사람에게)

| 선 | 조건 |
|---|---|
| **반복** | 같은 단계 · 같은 원인 2회 연속 — 횟수가 남아도 멈춘다 |
| **총량** | 한도 소진 |
| **경계** | 고칠 대상이 보호 영역 · 종료 조건 · 기존 테스트 기대값 — 0회차에도 |

**소진의 기본 해석은 "계약이 틀렸다"** 이다. 세 번 실패했다면 보통 종료 조건이 기계적으로 갈리지
않거나 배경이 틀렸다. 코드를 더 미는 것이 아니라 계약을 고칠지 묻는다.

### 세션이 끊겨도 이어받는다

세션은 언제든 끊긴다. 그때 남는 것은 **Issue 와 git 뿐**이다.
그래서 루프 상태는 세션이 아니라 **이슈 댓글에 쓴다.**

- 실패할 때마다 댓글 하나 — 회차를 첫 줄에 박는다
- 새 세션은 **마지막 루프 댓글의 회차를 이어받는다.** 댓글이 없으면 0 회차
- 회차를 세지 못하는 상태면 그 자체로 멈춤 — 모르는 채로 재시도하지 않는다

```
루프 2/3 · Test 실패 · popup-plan-stock > 불변
시도: 반출서 저장 경로에서 applyMovement 호출 제거
다음: 종료 조건 "불변" 줄이 관찰값인지 확인
상태: 커밋 없음 · 작업 트리에 변경 있음
```

멈출 때는 사람이 처음부터 읽지 않아도 되게 한 댓글에 다 담는다.

```
막힘 · 루프 3/3
실패: npm run verify → Test · popup-plan-stock > 불변
시도: ① … ② … ③ …  (각각 왜 실패했는지)
가설: 종료 조건 "불변" 줄이 관계식이 아니라 관찰값이다
필요한 결정: 종료 조건을 고칠까요, 구현을 계속할까요  (질문 하나)
상태: 커밋 없음 · 작업 트리에 변경 있음
```

끝났을 때도 **쓴 횟수를 남긴다** (`루프 1/3 사용`). 한도가 사후에 검증 가능해지고,
어떤 종류의 작업이 몇 회를 먹는지가 쌓인다.

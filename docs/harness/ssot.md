## 4. Issue — 개별 작업의 SSOT

이 문서는 **제품**의 SSOT, Issue 는 **한 작업**의 SSOT.
작업 중 판단이 갈리면 Issue 를 먼저 본다. 여기 없는 것은 작업 범위가 아니다.

| 물음 | 어디를 보나 |
|------|-----------|
| 제품 전체로 무엇을 만드나 | 이 문서 §1 |
| 이번 작업이 왜 필요한가 | Issue 1. 배경 |
| 어디를 고치나 | Issue 2. 변경할 내용 |
| **무엇이 참이면 완료인가** | Issue 3. 종료 조건 |
| **무엇이 완료를 판정하나** | Issue 4. 기계 검증 |
| 어디까지 고치면 안 되나 | Issue 5. 건드리면 안 되는 것 |
| 몇 번까지 재시도하나 | Issue 6. 구현 루프 |

### 규칙

- **6개 항목이 비면 시작하지 않는다** — 계약이 없으면 완료를 판정할 수 없다
- **Issue 와 이 문서가 충돌하면 이 문서가 이긴다** — 고칠 것은 Issue 다. 작업이 스펙을 바꾸지 못한다 (§3)
- **Issue 범위 밖을 고쳐야 하면 새 Issue** — 조용히 넓히지 않는다
- **종료 조건은 §6 검증 명령이 판정한다** — 붙일 명령이 없는 줄은 종료 조건이 아니다
- **종료 조건에 고정 숫자·고정 날짜를 쓰지 않는다** — 그 한 케이스만 맞아도 통과해 버린다. 관계식으로 쓴다

## 6. 검증

보호 영역이 바뀌면 CI 가 경고를 남긴다. 막지는 않는다 — 승인은 PR 리뷰에서 한다 (§3).

# 이슈 댓글 양식

**댓글을 달기 직전에 이 파일을 열고 그 양식 그대로 쓴다.**

왜 양식이 있나 — 세션이 끊기면 남는 것은 Issue 와 git 뿐이고, 다음 세션은 **첫 줄만 보고** 회차를
복원한다 (loop.md §5). 산문으로 적으면 나중에 찾지 못한다. 그래서 **회차를 첫 줄에 박는다.**

명령: `gh issue comment <N> --body-file <파일>` — 여러 줄이므로 `--body` 로 밀어넣지 않는다.

상태의 원본은 **댓글**이고 라벨은 색인이다. 둘이 어긋나면 댓글이 이긴다.

---

## 1. 루프 시작 (§3)

```
루프 시작 · 0/3
계약: 종료 조건 4줄 · 판정 npm run verify
```

`0/N` 의 N 은 계약 6번. 이 댓글이 없으면 루프는 아직 열리지 않은 것이다.

---

## 2. 회차 실패 (§5) — `npm run verify` 가 깨질 때마다 하나

```
루프 1/3 · Types 실패 · tests/expiry-list.test.ts:70
원인: `l.status !== 'OK'` — ExpiringLot.status 가 'EXPIRED' | 'SOON' 이라 'OK' 와 겹칠 수 없다. 타입이 이미 보장하는 것을 런타임으로 확인하려 했다
다음: 그 단언을 지우고, 정상 로트 제외는 경계 밖 날짜(OUTSIDE_AT)로만 확인한다
상태: 커밋 없음 · 작업 트리에 변경 있음 · 브랜치 issue-5-expiry-page
```

| 줄 | 넣는 것 |
|---|---|
| 1 | `루프 n/N · <단계> 실패 · <파일:줄 또는 테스트 이름>` — 단계는 Prepare · Types · Lint · Test · Build 중 하나 |
| 원인 | **왜 깨졌나.** 증상이 아니라 원인. 여기가 「같은 원인 2회 연속」(반복 멈춤선)을 판정하는 근거다 |
| 다음 | 다음 회차에 무엇을 고칠지 한 줄 |
| 상태 | 커밋 여부 · 작업 트리 · 브랜치. 다음 세션이 처음 확인할 것 |

## 3. 회차 통과 · PR (§6)

```
루프 2/3 · 통과 · PR #6
구현: getExpiringLots() (lib/inventory.ts) · /expiry 페이지 · 테스트 3건
계약 이탈: 2번이 지목한 lib/expiry.ts 대신 lib/inventory.ts — 그 파일은 클라이언트 컴포넌트가 import 해서 db 를 넣을 수 없다 (PR 본문 참고)
상태: 커밋 e4c5252 · 브랜치 issue-5-expiry-page · CI 대기
```

이탈이 없으면 그 줄은 빼지 말고 `계약 이탈: 없음` 으로 적는다 — 침묵과 확인이 구분되지 않으면 안 된다.
PR 번호를 반드시 넣는다. 이것이 PR 진입 조건 세 번째다.

## 4. NEED_HUMAN (§4) — 멈추는 모든 경우

여섯 가지뿐이다: `모호` · `충돌` · `경계` · `반복` · `환경` · `소진`.

```
NEED_HUMAN · 모호 · 루프 0/3
막힌 것: 종료 조건 3번 "재고가 모자라면 경고한다"
후보:  A · 입력 > 보유 → 경고   (tests/… > 보유 초과면 경고한다)
       B · 보유 0 → 경고        (tests/… > 재고 없으면 경고한다)
질문:  A 인가요 B 인가요
해둔 것: 1·2·4번 확정, 테스트 골격 작성까지
상태:  커밋 없음 · 작업 트리에 변경 있음
```

발행 조건은 **둘 다 참일 때만** — ① 저장소 안에서 확인 불가(코드·문서·git 을 읽어 답이 나오면 내가
찾는다) ② 답에 따라 결과물이 달라짐. 사람만 답할 수 있는 것은 **요청자의 의도 · 업무 규칙 · 우선순위**다.

금지 셋 — 저장소를 안 읽고 던지기 / 답에 걸리지 않는 부분까지 멈추기(**의존 없는 것은 다 해놓고** 던진다) / **질문 2개 이상**.

소진일 때는 `후보` 자리에 **시도 전부와 각각 왜 실패했는지**를 적는다:

```
NEED_HUMAN · 소진 · 루프 3/3
막힌 것: 종료 조건 4번 "불변" 이 기계적으로 갈리지 않는다
시도:  1회차 · 합계 비교 → 조회가 캐시를 타서 같은 값이 나온다
       2회차 · Movement 건수 비교 → 다른 테스트의 씨앗에 걸린다
       3회차 · 트랜잭션 격리 → prepare 가 매번 시드를 다시 깔아 판정 불가
질문:  불변 줄을 "조회 전후 Lot 합계가 같다" 로 좁혀도 되나요
해둔 것: 정상·경계 두 줄은 통과 (tests/…)
상태:  커밋 없음 · 브랜치 issue-7-…
```

라벨을 함께 붙인다: `gh issue edit <N> --add-label need-human`.
재개할 때 뗀다: `--remove-label need-human`. **해제는 사람의 댓글로만 난다** — 스스로 풀지 않는다.
답이 없으면 재촉하지 않는다. 기다림은 회차를 쓰지 않으므로 다른 이슈로 가도 된다.

## 5. LLM review (§8) — 받은 다섯 줄을 그대로

머리글 한 줄 + 본문 네 줄. 양식과 표식은 `review.md` 에 있다. **이슈 댓글이 원본이고 PR 코멘트는 복사다.**

```bash
gh issue comment <N> --body-file review.txt
gh pr comment <PR> --body-file review.txt
```

## 6. 루프 종료 · 요구사항 변경 (§3-2) — 사람이 계약을 바꿨을 때

차감하지 않는다. 루프가 그 자리에서 끝난다. **AI 는 재개하지 않는다.**

```
루프 종료 · 요구사항 변경 · 2/3 사용
바뀐 것: 종료 조건 3번 — "경고한다" → "저장을 막는다"
요청: 이 이슈를 닫아 주세요. 이어서 하려면 새 Issue 로 열어 주세요
상태: PR #12 · 머지하지 않음
```

바뀐 요구사항을 같은 PR 에 얹으면 그 PR 이 무엇을 만족시켰는지 아무도 판정할 수 없다.

## 7. 선택 기록 (§6 세 갈래) — 사람이 고른 뒤

판정(④·⑥)과 자문(⑥-b)은 기록이 남지만 **선택은 사람 머릿속에만 남는다**. 그래서 한 줄로 남긴다.
고르는 것은 사람이므로 **사람의 말을 받아** 적고, 권고와 다르게 골랐어도 그대로 적는다.

```
선택 ② 다시 구현 · 루프 2/3
근거: 리뷰 「거부 ⚠」 타당 — 지정 에러가 아니다
```

머지로 닫을 때는 쓴 횟수를 남긴다 (`루프 2/3 사용`) — 한도가 사후에 검증 가능해지고, 어떤 작업이
몇 회를 먹는지가 쌓인다.
